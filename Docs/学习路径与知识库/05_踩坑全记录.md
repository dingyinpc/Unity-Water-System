## A.  Shader / HLSL

### ★A-1 `SV_Position` 在片元阶段是**像素坐标**，不是裁剪空间

- **现象**：水面永远发奶白、不透。屏幕空间折射采到的画面纹丝不动，深度项看起来完全失效；换任何水面颜色参数都只是"换个颜色的奶白"。持续了多个开发日。
- **真因**：结构体里用 `float4 position : SV_POSITION` 同时当"光栅化位置"和"裁剪空间坐标"用。到了片元函数，`SV_Position.xy` 已经是**像素坐标**（0..1920 / 0..1080），`/w` 得到的 `screenUV` 是个巨大的数，折射 UV 和 `SampleSceneDepth` 全部取到画面角落的污染值。
- **解法**：结构体里**另带一份裁剪坐标**：
  ```hlsl
  struct WaterVaryings {
      float4 positionCS : SV_POSITION;   // 光栅化用
      float4 clipPos    : TEXCOORD3;     // 屏幕空间采样必须用这个
      ...
  };
  // domain shader:
  o.positionCS = TransformWorldToHClip(gr.pos);
  o.clipPos    = o.positionCS;
  // fragment:
  float4 posCS = IN.clipPos;
  ```
- **教训**：**语义名决定了值的含义**，同一个值在顶点/几何/片元三个阶段不是一回事。屏幕空间效果（折射、深度重建、抓屏）永远要自己把裁剪坐标传下去，别蹭 `SV_Position`。
- **连带影响**：这个 bug 掩盖了下游所有判断——我基于它产出的"深度诊断数据"得出过"深度纹理取不到"的错误结论（见 I-1）。**先确认观测通道可信，再解释观测结果。**

### A-2 噪声梯度声明成 `float` 却按二维用

- **现象**：`invalid subscript 'y'`。
- **真因**：`float du = ...;` 然后写 `du.y`。
- **解法**：`float2 du = 6.0 * f * (1.0 - f);`。同理二维方向向量只有 `.x/.y`，写 `.z` 也报 `invalid subscript`。

### A-3 HLSL 不允许函数内定义函数

- **现象**：`syntax error: unexpected token '('`。
- **解法**：把内层函数提到文件作用域。

### A-4 波浪参数数组不落盘

- **现象**：材质面板里 `_Waves` 永远是零值，几何波完全不推动；但重启后"看起来有波"（其实是细节法线在动）。
- **真因**：该编译配置把 `_Waves` 当**标量 Vector 属性**处理，`GetVectorArray` 返回长度 1，`SetVectorArray` 只对第 0 条生效且不序列化。
- **解法**：波浪改成 **shader 内置固定波**（A/ω/Q 硬编码）+ `_WaveAmpScale` 一个幅度旋钮。
- **教训**：Unity 材质数组的序列化行为跟 shader 里的声明方式强相关。**验证方式是"重启后还在不在"**，不是"这一帧看着对"。

### A-5 细分因子按固定倍率 → 三角形爆炸

- **现象**：FPS 崩到 1.7，水体画不出来。
- **真因**：`_MaxTess=12` 套在 40m 池塘、基边 0.42m 上 → 细分到 3.5cm 微型三角 → 百万级面。
- **解法**：按**目标世界尺寸**自适应：`factor ≈ 基边长 / _TessTargetSize`。任何网格分辨率都收敛到同一三角形密度。
- **教训**：曲面细分预算要按"屏幕上多大"定，不是按"细分几次"定。

### ★A-6 高频噪声放在**顶点**里算 → 整个潭面裂成"风车"

- **现象**：水面出现 10~12 个从中心辐射的明暗扇区，**边界是直线**，像电扇叶片。
- **真因**：`SkinNormal()` 写在**顶点着色器**里再插值。涟漪噪声特征尺度约 0.1m，而水面网格顶点间距 0.3~0.6m —— **严重欠采样**。每个三角形只拿到三个角上互不相干的法线，插值出一片线性渐变，相邻三角形朝向突变 → 直线边界。
- **解法**：皮肤法线移到**片元**里逐像素算（`worldPos` 已插值好，直接求值）。
- **教训**：**任何"细节"噪声都必须逐像素求值**，除非它的特征尺度明显大于网格间距。
  更值得记的一点：Main 那版水面为了省开销一直把法线混合放在顶点，**只是被 0.2m 的大振幅掩盖了**；把波幅降到 1cm、水面变平静之后，扇区问题立刻暴露。
  → **"为性能做的简化"常常不是更快，而是把 bug 藏进了某个参数区间。**

### A-7 `SampleTexture2D` 不是 URP 的宏，而失败是无声的

- **现象**：`Shader error in 'WaterProject/Water_Pond': undeclared identifier 'SampleTexture2D' (on d3d11)` —— 但编辑器里水面**照常渲染**，只是"有点不对"。
- **真因**：宏名写错（应为 `SAMPLE_TEXTURE2D(tex, sampler, uv)`，贴图在前采样器在后）。shader 编译失败时 Unity 会**继续用上一个成功编译的变体**，所以画面不会变黑。
- **教训**：**"画面看着还行"完全不能证明 shader 编译通过。** 必须去 `Editor.log` 搜 `Shader error in`（见 G-14）。

### A-8 变量名叫 `line` 会炸，但报错指向**下一行**

- **现象**：`syntax error: unexpected token 'line' at Beach_Sand.shader(100)`，紧跟一条 `'saturate': no matching 0 parameter intrinsic function`。第 100 行看上去完全正常。
- **真因**：`line` 在 HLSL 里是保留的语义关键字（几何着色器的图元输入），拿它当变量名，编译器不会说"重名"，而是把这一行从中间截断，于是**真正的错报到下一行去找 `saturate` 的参数**。
- **解法**：改名 `band`。
- **教训**：HLSL 报"unexpected token X"而 X 恰好是你自己的变量名时，**错就在 X 声明那一行，不在报错那一行**。同类保留字还有 `sample`、`filter`、`centroid`、`linear`。

### A-9 天空盒的视线方向**不能**用 `世界坐标 - 相机位置`

- **现象**：换上新写的天空材质之后，整片天空纯黑 —— 不是洋红、不是没材质，是黑。而且日志里**没有任何编译错误**，材质也确实指向了新 shader。
- **真因**：顶点里写了 `o.dir = TransformObjectToWorld(v) - _WorldSpaceCameraPos`。URP 的 `DrawSkyboxPass` 走的是 `context.CreateSkyboxRendererList(camera)`，那颗天空立方体的 `unity_ObjectToWorld` **不是**"平移到相机"那种可依赖的形式；减完剩下的是一个近似常量的向量，`normalize` 之后整个半球算出同一个方向，多数像素落进 `d.y < 0` 分支或者数值退化 ⇒ 黑。
- **解法**：直接取物体空间顶点当方向 —— `o.dir = v.positionOS.xyz`。工程里已经在跑的 `Sky_SimpleBlue` 就是这么写的，照它来。
- **教训**：**"编译通过 + 材质绑定正确 + 画面纯黑"这一组症状，指向的是几何/矩阵约定错了，不是着色器逻辑错了。** 而工程里已经有一个能跑的同类型资产时，先去看它怎么做的，比推演引擎内部快一个数量级。

### ★A-10 同名 cbuffer **不会**被合并，两个 `UnityPerMaterial` = 整个 shader 编译失败

- **现象**：海面与沙滩整片品红（255,0,255）。改动只有一处：把共享 include `OceanShore.hlsl` 里的 `CBUFFER_START(OceanShore)` 改名成 `CBUFFER_START(UnityPerMaterial)`。
- **真因**：我以为"URP 的 `CommonMaterial.hlsl` 就是 include 里开一个 `UnityPerMaterial`、各 shader 再开一个同名块"。**这个类比是错的**（见 I-13）。它开的是**另一个名字** `UnityBuiltinPerMaterial`。fxc/DXC 对同名 cbuffer 的答复是 `Duplicate constant buffer declaration: UnityPerMaterial`，硬错误。
- **解法**：共享 include **一个 uniform 都不声明**；宿主 shader 在自己的单块 `UnityPerMaterial` 里先声明那 10 个名字，**再** include。这条规则已写进 `OceanShore.hlsl` 头部，并且 `Tools/audit_materials.py` 第⑨项会机器检查（一个编译单元里 >1 个 `UnityPerMaterial` ⇒ ERROR）。
- **教训**：SRP Batcher 要的是"一个材质一个 `UnityPerMaterial`"，**不是**"每个 include 都开一个"。而"某某主流框架就是这么写的"这类记忆，动手前必须去包里 grep 一遍原文。

### A-11 HLSL 自上而下解析：include 的函数看不到 include **之后**声明的 uniform

- **现象**：改成"宿主自己声明"之后，报 `undeclared identifier '_Shore'`，指向 `OceanShore.hlsl` 里 `ShoreZ()` 的第一行。
- **真因**：把 `#include` 放在宿主 CBUFFER 之前是直觉写法，但 HLSL 不像 C++ 有前置声明兜底 —— 该文件自己的函数体先于声明被解析。中间还试过一版"`#define OCEAN_SHORE_PARAMS` 多行宏、宿主在块里展开"，看似优雅，实际等价于"声明在 include 之后"，同一个错。
- **解法**：`CBUFFER_START(UnityPerMaterial) …10 个声明… CBUFFER_END` **在前**，`#include "OceanShore.hlsl"` **在后**。
- **代价（已知并接受）**：那 10 个名字在两个 shader 里各抄一份。但它们在 `Properties{}` 里本来就要各抄一份（第⑧项管的就是这个），所以并没有新增一类重复；而抄漏的失败模式是**编译报错**，不是静默错值。

## B.  URP 与渲染配置

### ★B-1 `VolumeProfile.Add<T>()` 不落盘，后处理整条静默空操作

- **现象**：ACES、postExposure、saturation 全部调了，画面**一个像素都没变**。反复怀疑"ACES 把画面压暗了"并据此做了一堆错误推理。
- **真因**：`profile.Add<T>()` 只创建内存对象，不调 `AssetDatabase.AddObjectToAsset()` 就永远不写进 `.asset`。结果 profile 里是 `components: [fileID: 0, fileID: 0]` 两个空槽。
- **解法**：
  ```csharp
  prof.components.RemoveAll(c => c == null);          // 清掉历史空槽
  ton = prof.Add<Tonemapping>();
  AssetDatabase.AddObjectToAsset(ton, prof);         // ← 关键
  ```
- **教训**：**"设置没生效"和"设置根本没被保存"是两回事**。验证方式是打开 `.asset` 看 `m_Component` 里有没有真实 fileID，或者做一次极端值测试（把 postExposure 设 -4，画面没变 = 通道不通）。

### ★B-2 Scene 视图不吃 Volume，只有 Play 的 Game 视图吃

- **现象**：在 Scene 视图里截图，改后处理参数数值不动。
- **验证**：把 `postExposure` 设成 `-4`，Scene 视图**零变化**；即使给 Scene 相机手动挂 `UniversalAdditionalCameraData` 并 `renderPostProcessing = true` 也没用。
- **解法**：**所有观感判断必须在 Play 模式的 Game 视图里做**（菜单43）。Scene 视图只能看构图和几何。
- **教训**：先验证观测通道，再验证被测量。这条和 A-1 是同一个错误的两种表现。

### B-3 URP 14 没有 `Fog` 的 VolumeComponent

- **现象**：写 `UnityEngine.Rendering.Universal.Fog` 编译报 CS0234。
- **真因**：URP 14 的 `Runtime/Overrides/` 里确实没有 Fog（只有 Tonemapping / ColorAdjustments 等）。
- **解法**：雾走 `RenderSettings.fog / fogMode / fogColor / fogDensity`。
- **教训**：**别凭记忆写 API**，先列一下目录确认组件存在。

### B-4 折射/深度需要 Opaque + Depth Texture

- **要求**：URP Asset 里 **Opaque Texture**（采屏幕空间背景）和 **Depth Texture**（算水深）都必须开。少一个就是水面纯贴图或奶白。

### B-5 阴影距离会把远景道具收进来

- **现象**：远岸草坡上出现一道道长条黑影；沙滩上横一条硬阴带。
- **真因**：`m_ShadowDistance = 140` + 太阳仰角 30°，于是 r30~50 的树、整圈远岸绿墙全在阴影投射范围内。
- **解法**：背景类物体（草坡、远树）统一 `shadowCastingMode = Off`。它们只需要剪影，不需要自投影。

### B-6 共面 z-fighting

- **现象**：陡视角下草地"吃掉"水面，Game 视图一片绿灰，水面取色被污染。
- **真因**：地面顶面 y=0 与水面圆盘 y=0 **完全共面**。
- **解法**：水面上浮 2cm（y=0.02），水面上的物件（荷叶）相对高度照旧。

## C.  光照与颜色校准

### ★C-1 ACES 的趾部会吞掉整个中间调

- **现象**：岩石阴影面实测 `(30,41,53)`，参考帧是 `(88,122,151)` —— 线性亮度差约 **8 倍**。
- **真因**：`postExposure 0.55` 太低，中间调整个落在 ACES 曲线的趾部里被压平。此时**无论怎么调反照率都拉不上来**（调高只会让亮的过曝、暗的还是死）。
- **解法**：先把 `postExposure` 抬到 1.15，**再**调反照率。
- **教训**：调色的顺序必须是 **曝光 → 光源 → 反照率**。反过来做会得到"参数怎么调都没用"的假象。

### ★C-2 "受光 ≈ 阴影"是天光填充的判据

- **现象**：岩石近黑，第一反应是"反照率太低"，改了三轮没用。
- **真因**：参考帧实测**受光岩 `(103,130,154)` ≈ 阴影岩 `(88,122,151)`**，差不到 1.2 倍 —— 说明那是个几乎平涂、天光主导的场景，而我们直射光占比过高、环境光过弱。
- **解法**：ambient sky 从 `0.22` 提到 `0.50,0.58,0.68`。
- **教训**：**先量参考帧的"明暗差比"，再决定是调光还是调材质。** 只看单点亮度会得出完全相反的结论。

### C-3 太阳仰角决定所有朝上面的亮度

- **现象**：岩石顶、树冠、沙面**集体**发黑。
- **真因**：太阳被压到仰角 14°，朝上面的 `N·L = sin14° = 0.24`。
- **解法**：仰角回到 30°。
- **教训**：**"很多物体同时暗"通常是光源问题，不是逐个物体的材质问题。** 找共因，别一个个调。

### ★C-4 同一个物理量被两个菜单各写一遍

- **现象**：明明改了菜单48 的太阳仰角，跑完整链还是暗的。反复怀疑"提 ambient 没用"。
- **真因**：菜单54（低机位）为了保碎闪**又写了一次** `Euler(14,208)`，而 54 在 48 **之后**跑 → 48 的值被静默覆盖。
- **解法**：**删掉菜单54 的赋值**，让菜单48 成为唯一来源；改由相机俯角去适配太阳仰角。
- **同类第二次**：`_FresnelPow` 由菜单40 设为 6，40 在 48 之前跑 → 必须在 48 里显式覆盖一行。
- **同类第三次**：菜单48 内部 `_SkyReflect` 有两行赋值（0.55 与 0.75），后者静默胜出。
- **教训**：**"几何耦合"不等于"要重复赋值"。** 全局参数要有唯一写入点；调试"改了没反应"时，第一件事是 **grep 这个属性名被写了几次**。

### C-5 脚本 `SetColor` 是线性空间

- **现象**：按 sRGB 目测取的颜色写进去，渲出来偏艳偏暗。
- **解法**：`Material.SetColor` / `.mat` 里的值都是**线性**；从截图取的 sRGB 要先转线性（`c ≤ 0.04045 ? c/12.92 : ((c+0.055)/1.055)^2.4`）。
- **教训**：所有最终值都应"经 Play 真实 Game 视图（含 ACES）取样校准"，不要靠换算直觉。

### C-6 大气透视 ≠ 变暗

- **现象**：远山调暗之后变成"黑三角"，逆光剪影生硬。
- **真因**：大气透视的正确方向是 **提亮 + 压饱和 + 偏蓝**，不是压暗。
- **解法**：`Hill_Distant → 0.34,0.42,0.46`（蓝 > 绿）。
- **配套判据**：**远景偏绿 = 反照率 G 抬太高而 B 没跟上。**

### C-7 ACES 的色相限制会把饱和色压成暗色

- **现象**：荷花给了 `(0.90,0.26,0.50)` 的"粉"，渲出来是**砖红**。
- **真因**：高饱和洋红/红色被 ACES 色相限制强烈压缩。
- **解法**：用**浅粉** `(0.92,0.56,0.66)` —— 提亮 + 降饱和才保得住。
- **教训**：想要某个鲜艳颜色，给它的输入要比直觉**更亮、更不饱和**。

### C-8 沙地"不像"往往是缺蓝，不是太亮

- **现象**：沙滩读成橙褐。第一反应"太亮了"，压暗之后变成脏灰。
- **真因**：蓝通道比参考低 27。
- **解法**：**补蓝**，不是降明度。
- **反向坑**：补过头（近中性 `0.46,0.45,0.45`）会让沙滩在蓝天光下洗成蓝白 —— 暖调要保留。

### ★C-9 "幽深"不等于"全都压暗"

- **现象**：要森林深处的幽深感，于是一路压：环境光压到 1/4、天空地平带从 0.34 压到 0.185、反射权重 0.95→0.80、岸色再压暗。每一步单看都"更暗更沉"，合起来画面却变成一滩糊住的绿，比改之前更平、更难看。
- **真因**：**没有任何一个区域是亮的**。实测八个取样框全部落在 `(12,37,23)`~`(81,70,33)` 这条窄带里，而其中"天空带"(42,59,36) 与"树冠"(40,62,30) **几乎同值** —— 地平带一旦不比树冠亮，"林子外面有光"这件事就消失了，深度层次跟着消失。
- **解法**：把亮度**跨度**拉开而不是把亮度**均值**压低：地平带回到 0.28（仍远低于开阔天的 0.34+），太阳从 2.2 抬到 3.0 只抬"被照到的那几簇叶卡"，环境光保持低位不动。抬强度在这里增加的是**反差**不是整体亮度，因为暗部由环境光决定、而环境光没变。
- **判据**：调暗调场景时，先量**最亮框 − 最暗框**，再谈平均亮度。跨度塌了就是画面塌了，跟"够不够暗"无关。
- **同类**：与 C-1（ACES 趾部吞中间调）是同一枚硬币的两面 —— 那次的错是把暗部压进趾部，这次的错是把亮部也拖进趾部。

### ★C-10 `lerp(地平, 天顶, pow(up, e))`：**调小 e 是往暗的方向走**

- **现象**：用户说"天空盒太暗了"。我判断"亮的地平色占的画面太少"，于是把指数从 2.0 降到 1.45 想"让亮色多撑一会儿"。实测顶缘 (124,159,202) → (113,…) —— **更暗了**。
- **真因**：`up` 在天顶=1、在地平=0。`pow(up, e)` 里 **e 越小值越接近 1**，而 1 对应的是 `lerp` 的**第二个**参数 = 天顶 = 暗色。所以降 e 是把整条可见带推向暗天顶，和意图完全相反。
- **解法**：回到 `up*up`；要提亮就提**地平色本身**（`(0.700,0.800,0.910)`）。ACES + postExposure 0.85 吃线性值很狠，线性 0.45 出来就是灰蓝 —— 天空要亮，得从反照率给，不是从曲线形状给。
- **教训**：改任何形如 `lerp(A, B, f(x))` 的混合前，先在纸上代两个端点值。**"我觉得这个参数变大是往亮走"在这个式子里两次里会错一次。**

### C-11 程序云的两条独立死法：数量级、以及用绝对值当亮度

- **症状一：云完全没有结构，整片天是一坨糊白**。`_CloudScale` 写了 0.045。顶缘投影平面 `plane = d.xz/d.y` 的长只有 ≈2.1，乘 0.045 = **0.096** —— 全画面采在同一个噪声单元里，等于没有噪声。正确量级是 0.9（差 20 倍）。这类错只能靠**先算一遍采样跨度**发现，看图永远只会得出"再调调覆盖率"。
- **症状二：一提覆盖率就整片洗白**。fbm 四倍频值噪声的取值天然挤在 0.55~0.72，云的颜色却按 `f` 的**绝对值**插值 —— 阈值一降，所有像素都同时变亮。改成按"越过阈值的厚度"着色：`thick = saturate((f - cover) / 0.28)`，向阳面亮、底面吃天光偏蓝。
- **判据**：任何"阈值 + 插值"的噪声效果，插值因子必须是**超出量**而不是**原始值**。否则阈值和外观是耦合的，永远调不到"又多有结构又可控"。

## D.  水面观感

> 这一类是本项目最贵的部分。水面是"一个 shader + 十几个参数"的耦合系统，**单点调参会互相掩盖**。

### ★D-1 高光无界累加 → 整块死白光斑

- **现象**：水面突然出现大片突兀的白色光斑。
- **真因**：两条叠加 ——
  ① `col += _SunColor * spec` 是**无界累加**，把本来就亮的水色顶过 1.0，被 ACES 削平成一片死白；
  ② 细节法线只有低频八度，**一大片面元朝向几乎相同** → 一起亮。
- **解法**：
  ```hlsl
  float spec = saturate(pow(saturate(dot(N,H)), _SpecPower) * _SpecStrength);
  col = lerp(col, _SunColor.rgb, spec);          // 有界：上限就是 _SunColor
  ```
  并加第三层高频八度把碎闪打碎成点。
- **教训**：**累加式高光必须设上界。** `lerp` 到光源色比 `+=` 安全得多。

### ★D-2 泡沫/深度带用"视深"算，低机位下直接消失

- **现象**：岩石水线处完全没有参考帧那种白沫领圈。
- **真因**：`gap = sceneDepth - waterDepth` 是**沿视线的距离**。低机位视线接近水平时，**1m 垂直水深被换算成 ~4m 视深**，泡沫带宽被压到约 17cm → 看不见。
- **解法**：先换算回垂直水深，带宽才与观察角度无关：
  ```hlsl
  float vd = gap * max(V.y, 0.12);
  float shoreFoam = saturate((1.0 - vd * 1.7) * (1.0 - fres) * 0.75);
  ```
- **教训**：**任何"按水深"的效果都必须显式区分垂直水深和视深。** 同一个 bug 还让吸收系数把整池判成深水（D-3）。

### ★D-3 `_Absorb` 作用在视深上 → 浅池全池"深水色"

- **现象**：水"不透"，而且**近岸比塘心还暗**（与参考帧完全相反）。
- **真因**：池子最深只有 1.30m，`_Absorb 1.9` 配视深使 `depthMix = 1-e^{-gap·1.9}` 全池 ≈ **0.92** → 浅滩也被当成深水。
- **解法**：`_Absorb → 0.85`（1.3m 处 depthMix ≈ 0.67）。
- **教训**：**吸收系数要按"这个池子实际多深"标定**，没有通用值。换个场景尺寸就得重标。

### ★D-4 碎闪"点不亮"是**角度**问题，不是强度问题

- **现象**：参考帧亮带 `med(208,218,201)` 近白，我们 `(69,149,171)`。
- **走过的弯路**：按直觉连抬 `_SpecStrength 1.1→1.7→2.0`、`_SunStrength 1.4→2.6→3.4`，实测只爬到 `(95,177,175)`，**几乎无效**。
- **真因**：两个**角速度**参数把高光限制在极小区域：
  - `_SunGloss 700` → `pow(cosδ, n)` 半高宽约 `1.3/n` 弧度 ≈ **±1.8°**，在 52° 视场里只占 4% 画面高度 → 太阳高光是**一条线**，不是**一片**；
  - `_FresnelPow 6` → 水面俯角 10° 时 `fres` 才 **0.33**，必须贴着地平线才趋近 1 → **画面绝大部分水面根本没在"照镜子"**，`col += skyCol*fres*_SkyReflect` 这条路径基本不成立。
- **解法**：`_SunGloss → 90`、`_FresnelPow → 4`、`_SkyReflect → 1.0`；并因覆盖面积涨约 8 倍把 `_SunStrength` **降回** 2.2，否则整幅洗白。
- **教训**：**"高光不够亮"先算它在画面那个几何条件下能取到多少**，再谈强度。再大的强度乘在 4% 覆盖率上还是一条线。

### D-5 "波瓣宽 = 光斑大"只在法线低频时成立

- **背景**：D-1 之后我们学到"波瓣要窄"，于是把 `_SpecPower` 拉到 900、`_SunGloss` 拉到 1500。
- **反例**：D-4 需要放宽波瓣，但没有重现死白。
- **真因**：细节法线已经是**三 octave、`_DetailScale 7.6`**，面元足够小足够密，放宽波瓣只会让点变多变亮。
- **教训**：**"波瓣宽度"必须和"法线频率"成对考虑**，不能单独当结论记。上一轮的"正确参数"可能是这一轮的瓶颈。

### D-6 透彻感 = 透明权重 + 折射位移上限

- **现象**：放大看"发糊、像蒙了层色膜"。
- **真因**：看穿湖底只有两条路——折射项（因 depthMix 饱和权重≈0）和未位移的 `sceneCol`（被 `_Opacity 0.95` 压到只剩 5%）；而 `_MaxUVOffset 0.12`（屏幕比例，906px 下 ≈108px）把任何折射都抹成一团糊。
- **解法**：`_Opacity → 0.76`、`_MaxUVOffset → 0.025`、`_RefractStrength → 0.3`。
- **教训**：折射位移上限是个**极敏感**参数，0.1 和 0.025 是"糊"和"透"的分界。

### D-7 浅滩发灰 = 池底色相问题，不是水面色问题

- **现象**：近岸浅滩带是灰的，参考帧是淡薄荷绿。
- **走过的弯路**：① 以为是盆缘破水 → 改 `Rim`；② 以为是台地硬边 → 砍抬升量；③ 以为是过曝 → 压沙色。**全部无效。**
- **定位方法**：在 Play 里 `setProperty active=false` **逐个隐藏** `Ground`/`PondBasin`/`BasinStep_*`，画面里那条带**完全不动** → 它不是独立物体；改 `_ShallowColor` 时它**跟着变** → 归水管。
- **真因**：折射层把池底大量混进水色，`Ground_Lake` 是暖褐 → 混出来发灰。
- **解法**：池底与水下沙材质改成**绿反超红**的黄绿沙。
- **教训**：**"排除法 + 单变量响应"比"猜测 + 修改"快得多。** 而且——对照参考帧后发现**构图A 底部本来就有这条浅滩带**，差点为一个不存在的问题重构盆底。

### D-8 交互涟漪的白圈

- **现象**：水面莫名冒出白色大圈。
- **真因**：演示模式每 0.45s 随机砸一次涟漪，shader 里交互泡沫以白色 `_FoamColor` 强叠。
- **解法**：demoInterval 0.45→4s、强度 0.5-1→0.18-0.42、`_InteractionAmp 0.35→0.22`、`_InteractionFoam 0.9→0.45`、尾叠乘数 0.4→0.12。

### D-9 水面"棋盘格"不是细分接缝

- **现象**：水面出现规则方格状接缝，第一反应是曲面细分的 patch 边界。
- **真因**：噪声函数**梯度不连续**（`frac`/`floor` 边界上导数跳变）。
- **解法**：改用值噪声的光滑插值（smoothstep 五次多项式）而非线性插值。
- **教训**：**"看起来像网格"不一定是网格拓扑问题**，先查函数连续性。

### ★D-10 倒影"淡出"参数恰好抹掉了唯一想倒的东西

- **现象**：平面反射明明在工作（调试通道里能看到树），但正常渲染时倒影淡得几乎看不见。
- **真因**：`_ReflFade = 45`（米）本意是"远处没内容时退回天空"。而树就在相机前方约 **24m**，淡出曲线在 24m 处已经削掉一半，越靠近对岸削得越狠 —— **正好作用在主体上**。
- **解法**：`_ReflFade → 120`（场景内基本不淡出），让"退回天空"只在真正超出几何范围时才发生。
- **教训**：**任何"按距离衰减"的默认值都必须对着场景实际尺度检查一遍。** 一个在开阔地形合理的经验值，放进 16m 见方的潭里就是自毁。

### ★D-11 倒影占多少水面是**几何**问题，不是着色器问题

- **现象**：反复调 `_PlanarStrength` / `_SkyReflect` / `_FresnelPow`，倒影始终只占潭面一条窄带。
- **真因**：水面某个像素能倒出什么，完全由"该像素的反射方向指向哪"决定。相机在 y=3.6、俯角 12° 时，潭面反射的是**抬头方向的空天**；对岸的树只张约 8° 仰角，于是只能倒进远岸一条窄带里。
- **解法**（两个都是几何的，不是调参的）：
  1. **降机位**：y=3.6→1.9、俯角 12°→7°，掠射角覆盖到潭心；
  2. **把树搬到岸边**：岸外 3.6~9.1m → 1.6~4.8m，仰角张角翻倍。
- **教训**：**先算几何，再调权重。** 用 `_DebugMode=1` 只看反射通道，一眼就能分辨"反射没算对"和"反射算对了但被 blend 掉了"—— 这两种情况的修法完全不同，靠猜会一直调错旋钮。

### D-12 水平镜面别用 Reflection Probe

- **现象**：想给水面加倒影，最省事的做法是场景里丢一个 Reflection Probe。
- **真因**：探针是**单点**立方图。对水平面，离探针越远视差误差越大 —— 岸上的树会倒映在错误的位置，且倒影不会随相机移动而产生正确的视差滑动。
- **解法**：水面这种近似的**无限大水平镜面**要用平面反射（镜像相机渲 RT）。URP 14 没有内置，官方文档给的做法就是"自己渲一台子相机到 RenderTexture"。
- **教训**：探针适合**有粗糙度的小物体**（石头、金属），不适合镜面。潭水的卖点就是镜面，所以这块必须自己做。

### ★D-13 反射写成"累加"，深色倒影就永远显不出来

- **现象**：调试通道里平面反射明明在工作（能采到山坡和树），合成到水面上却只剩一片发白，越掠射越白。
- **真因**：`col += reflection * fres * _SkyReflect`。累加**只能变亮**，而掠射区映的偏偏是比水色更暗的山坡 —— 于是"反射最强"的地方恰好被反射**洗白**，方向完全反了。
- **解法**：改成能量守恒的**替换**：`col = lerp(col, reflection, saturate(fres * _SkyReflect))`。掠射时水面"变成镜子"，而不是"在水色上再叠一层天"。
  同时把**太阳反光带从天色里拆出来单独累加**：碎闪本质是加光，而且不拆的话它会在 `planar` 接管时被上面那条 lerp 一起抹掉。
- **教训**：`+=` 和 `lerp` 不是风格差别。凡是"这一项会盖掉下面"的物理量（反射、折射、泡沫、高光），**必须用 lerp**；只有"额外加进来的光"（自发光、碎闪）才用 `+=`。同一条规律在 D-1（高光无界累加）上以相反的形式出现过一次。

### ★D-14 镜像相机的姿态：把 `up` 的 y 取反喂给 LookRotation，等于多滚 180°

- **现象**：反射的内容是对的（树、岸、天都在），但整幅**上下颠倒** —— 地面在画面上方、天空在下方。因为倒影被压在水面附近，肉眼只表现为"反射带的位置总是差一截"，很容易误判成 UV 算错。
- **真因**：`Quaternion.LookRotation(new Vector3(fwd.x, -fwd.y, fwd.z), new Vector3(up.x, -up.y, up.z))`。反射后的 (right, up, fwd) 三轴组是**左手系**，`LookRotation` 会强行右手化，效果是**同时把 right 和 up 取反** —— 那正是绕视轴滚 180°。
- **解法**：水平面镜像的标准式直接对欧拉角动手：**pitch 取反、roll 取反、yaw 不变**，位置单独按 y 翻折。
  ```csharp
  Vector3 e = main.transform.rotation.eulerAngles;
  transform.SetPositionAndRotation(
      new Vector3(p.x, 2f * waterHeight - p.y, p.z),
      Quaternion.Euler(-e.x, e.y, -e.z));
  ```
  （无 roll 时等价于 `LookRotation(mirrorFwd, Vector3.up)` —— 关键就是**不要**用"取反后的 up"。）
- **教训**：镜像矩阵 `det = -1`，**任何**"把反射后的轴直接拼成旋转"的写法都必须显式处理手性。手算三轴看着最省事的写法，恰恰是最容易把手性错当成滚转的。

### ★D-15 斜投影裁剪平面"取反让相机落在正侧"，会把保留的半空间反过来

- **现象**：倒影里对岸的树全都不见了，取而代之的是一块**巨大的、边界光滑的椭圆暗块**，正好盖住整条本该是山坡倒影的水面。第一反应是"阴影坏了"或"反射强度不对"。
- **真因**：照抄「Plane Clipping in 3 Steps」时顺手加了一句防御 —— `if (p.w < 0) p = -p;`（"斜投影要求相机在平面正侧"）。但**镜像相机本来就在水面以下**，水面相对它就是它的**近平面**，带符号距离为负是正常状态（任何相机的近平面都在它前面）。取反之后保留的半空间从"水面上方"翻成"水面下方"，于是 RT 采到的正是**潭底自己的底盘**（`PoolBasin`，橄榄色反照率 × 弱光 ≈ `(33,39,29)`，与那块暗块实测一致）。
- **解法**：**只归一化，不改符号**。世界平面给 `(0, 1, -waterHeight)`（水面上方为正）就一路用到底。
- **教训**：抄来的公式里那些"看起来像防御性修正"的行，必须逐条问"它在我这个坐标系约定下还成立吗"。这里的判据其实很便宜：**把 RT 导出来看一眼**就知道反射内容对不对（见 G-15），而当时我在水面上反复调反射强度，调的是合成、坏的是裁剪。

### D-16 远岸那道"灰带"是逆光坡面被蓝色环境光主导，不是几何

- **现象**：水线上方横一条失饱和的灰带（实测 `(110,118,119)→(99,106,106)`），而它后面平坦的岸顶是 `(211,201,177)`。看着像"多了一层水泥台"，Main 里同类现象的真因正是几何。
- **真因**：太阳在 `Euler(30,208)`（对岸那一侧）。远岸沙坡朝 `-z`、坡度 23°，`N·L` 只有 **0.16** → 漫反射几乎全靠三光源环境光，而环境光是蓝的 `(0.50,0.58,0.68)` → 暖沙被洗成灰。
- **解法**：把太阳移到**相机后上方** `Euler(48,336)`，远岸坡面 `N·L≈0.92`。顺带平面反射里映出的也是受光的坡面而不是暗块。
  **代价与连带修正**：受光面亮度一次涨约 5.7 倍，沙地直接打到截顶 `(255,255,239)`、岩石 `(171,225,255)` → 太阳强度必须同步 `2.5 → 1.4`（让同反照率的岩石落回 Main 的实测族 `(103,130,154)`）；草坡反照率 `(0.055,0.300,0.100) → (0.075,0.250,0.115)` 去饱和，否则读成霓虹绿。
- **教训**：换光位**不是**只改一个数。它同时改了：所有朝上面的亮度、阴影投向、镜面带的落点，以及反射**内容**的亮度。改完必须重新走一遍曝光族取色，而不是"看着亮了再压"。
- **另注**：掠射碎闪要求"太阳仰角 ≈ 视线俯角"。这台低机位约 5~7°，而潭水 `_SunGloss 260` 的半高宽只有 ±0.3°，抬到 48° 后水面基本不再有太阳反光带 —— 林间静潭本就该如此，**这是取舍不是 bug**。

### D-17 掠射区的涟漪"灯芯绒"是**混叠**，不是强度太高

- **现象**：潭水中部一排排等距的横向暗纹，像灯芯绒。第一反应是 `_RippleStrength` 太大，调小之后近处的细节也一起糊掉。
- **真因**：水面是个平面，所以 `abs(V.y)` 越小就越掠射、也就**等价于越远**。此时 `1/_RippleScale ≈ 0.18m` 的毛细格投到 896px 画幅上只剩 1~2 像素，`NoiseSlope` 的前向差分梯度直接混叠成等距条纹。
- **解法**：给 `SkinNormal` 加一个高频层权重 `fineW = lerp(0.20, 1.0, smoothstep(0.05, 0.40, abs(V.y)))`。中频缓波不动（远处倒影总得有点扰动），只削高频层。
- **教训**：**同一个"强度"旋钮在屏幕上的等效频率是随视角变的**，要按视角分档，不能全局调。与 D-9（棋盘格 = 噪声梯度不连续）、E-8（尺寸按像素反推）是同一条规律的三个面。

---

### D-18 天空那条带是**几何**问题，靠雾而不是靠颜色

- **现象**：画面顶缘一条约 11° 高的空天。先试着压暗 `_HorizonColor`，压到 0.185 时整幅掉进一条窄绿带（D-16 的教训），此路不通。
- **真因**：机位 fov 46°、俯 7° ⇒ 画幅上缘只到仰角 **16°**，而绿坡脊线只顶到约 **5°**。要在近处闭合，就得 `r<25m` 连一排 12m 高的树 —— 会把中圈树墙和潭岸全挡死。
- **解法**：往**远处**挂两层噪声顶缘幕帘（`菜单68 → BuildTreeline`，r=50/66、240 段、顶缘 3θ/9θ/21θ 三组倍频 + 一个林窗包络让某些方位整片矮下去）。这两个半径上指数方雾的透过率只剩 **13% / 8%**，颜色被自动压成雾色 ⇒ 天然读成"雾里的树梢"。**一行远景淡出代码都不用写。**
- **教训**：想要"大气透视"就先造"距离"。雾是引擎免费给的远景混合器 —— 只要把东西放到雾足够浓的距离上，它自己就会变成剪影。反过来，任何"给材质加个远景淡出"的冲动，都应该先问一句：能不能把东西放远点。

### D-19 碎浪判据拿**三条浪的波高之和** ⇒ 整片海变一张白纸

- **现象**：海岸第一版，海面从水线一直白到地平线附近，完全没有"海"的颜色。
- **真因**：`breakage = hSum/depth > γ` 里的 `hSum` 累加了全部三条 Gerstner 波（λ 150/74/24m），得到 H≈3.8m；配上海床坡度只有 0.055（水深 4.7m 出现在离岸 85m 处），于是**离岸 85m 以内全部判为正在破碎**。物理上破碎判据针对的是"这一列浪"，不是"所有浪叠加的总高度"。
- **解法**：破碎**深度**只用主浪的波高 `2·a₀·gain`；破碎**条带的相位**另说（见 D-20）。
- **教训**：多分量模型里任何一个"阈值判据"都必须明确它作用在**哪一列**上。把叠加总量喂给一个按单列标定的阈值，结果不是"稍微过一点"，而是整片饱和。

---

### D-20 沫带用无符号的"往岸上多远"算 ⇒ 海侧恒为满沫

- **现象**：紧接 D-19 之后海还是白的，但这次白色覆盖了**整个洋面**，连深水区都是。
- **真因**：`up = max(-offDist, 0)` 在海侧（offDist>0）恒等于 0，于是 `swash = 1 - up/reach` 在海侧恒等于 1 —— 冲滩沫带被铺到了地平线。
- **解法**：沫带必须用**有符号**的离岸距离：岸上往回衰减 `reach` 米，海侧只保留约 3m（刚退下去的那层湿沫），再往外是干净的水。
- **教训**：凡是"以水线为原点往两侧不对称衰减"的量，就不能先 `max(...,0)` 再拿它当距离用 —— 那等于把一侧的坐标全部折叠到原点。**折叠过的量只能用于显示，不能用于判据。**

### D-21 碎浪白线的"排数"由最短浪决定，不是由破碎带宽度决定

- **现象**：修完 D-19/D-20，海有颜色了，但碎浪只剩水线边一道糊白，读不出"一排排浪向岸推进"。
- **真因**：条带相位挂在主涌 λ=150m 上。破碎带从外缘到水线一共才几十米，**150m 的波长在这个区间里连一个波峰都放不下**，所以数学上只可能有一条线。
- **解法**：条带相位改挂 λ=24m 那条短浪（`k0 = 2π/24`），破碎深度仍然按主浪算 —— 两件事分开。于是沙坝上先碎的是短浪，画面里出现 2~3 道平行白线，正是海滩真实的样子。
- **教训**：**"要几条线"是波长问题，不是强度问题。** 想在某个空间区间里摆出 N 个特征，特征波长必须 ≤ 区间/N —— 和 E-8"尺寸要按像素反推"是同一条约束，只是这次量的是世界空间。

## E.  程序化几何与地形

### ★E-1 绕序反了 → 整片沙滩"消失"

- **现象**：俯视机位一抬高，水外面全是草地而不是沙。第一反应是"沙的颜色不对"。
- **真因**：探针实测 `ShoreSandRing avgNrmY = -1.000`、`PondFloorShore avgNrmY = -1.000`，而 `Sand_Shore.mat` 是 `_Cull: 2`（背面剔除）→ **沙滩根本没被画出来**，露出的是下面 y=-0.5 的草地。
- **解法**：菜单46 统一把地面网格绕序翻正 + 显式朝上法线（`avgNrmY → +0.977`）。
- **教训**：**"看不到"和"颜色错"是完全不同的故障。** 低机位之所以"看着有沙"，是掠射角下前向面恰好可见 + 看到的其实是池底。**先确认它被画了，再谈画得好不好。**

### ★E-2 同心台地 → "靶心"/体育场

- **现象**：为了做凹陷感加了三圈同心台地，结果看着像体育场或波纹槽，完全不像挖出来的沙坑。
- **真因**：等参数 t 生成的同心环**过于规则**。
- **解法**：`WobA(th, seed)` —— 三组低频正弦（2θ/5θ/9θ，相位取自稳定哈希 `Hash11`）合成**平滑**角向扰动，**同时作用于盆底等深线和台地边界**，让两者沿同一套轮廓走、不错位穿帮。
- **教训**：**程序化地形要"不规则"，但必须用低频平滑函数扰动**；直接叠逐顶点随机噪声会变成麻点。

### ★E-3 高频起伏 + 平面着色 = moiré 条纹

- **现象**：远岸草坡坡面出现一道道同心明暗条纹。
- **真因**：上缘用了 `11θ + 23θ` 高频正弦，在平面着色 + 256 段的网格上**被打拍成 moiré**。
- **解法**：降到 `3θ + 7θ` 低次谐波。
- **教训**：**着色频率决定了几何细节的上限。** 平面着色下任何高于网格采样率一半的细节都会折叠成假条纹。

### E-4 重合顶点 → 退化三角 → 零法线

- **现象**：`RecalculateNormals()` 之后一半顶点法线是零，渲染出淡青横带和斜向尖刺。
- **真因**：网格构造时同一位置塞了多个顶点（内壁/顶/外壁共用坐标），产生退化三角；`RecalculateNormals` 对退化面得到零法线（实测 294/582 为零）。
- **解法**：**显式给法线**，或保证三角形非退化。
- **配套**：非索引化（每三角形独立顶点）+ `RecalculateNormals` = 逐面法线 = 想要的低多边形平面着色。

### E-5 台地是"深度突变"，水一透就露馅

- **现象**：水面透明度提上来后，近岸出现笔直的灰白分界线。
- **真因**：每圈台地的外缘都是一次**深度不连续**，透明水面会把它直接画出来。
- **解法**：抬升量 `0.055+0.075t → 0.010+0.016t`（约 1/5），凹陷改由锥形盆底单独承担。
- **教训**：**几何细节的可见性取决于覆盖它的介质透明度。** 水面变透 = 一次性暴露所有水下几何的硬边。

### E-6 盆底边缘与水面共面 → 破水而出

- **现象**：近岸糊出一道"水泥台阶"。
- **真因**：盆底 `Rim = +0.02` 正好等于水面高度 y≈0.02 → 完全共面。
- **解法**：`Rim → -0.07`，让盆体外缘**低于水面**。

### E-7 道具贴合：采样网格，不要复制公式

- **现象**：改了盆底剖面之后，探针审计出 **19 件悬空**（7 块深水巨石底面高出新盆底 0.16~0.47m、4 株荷叶落到干滩）。
- **走过的弯路**：想再写一个高度公式来算贴合。
- **真因**：水面/沙环的半径公式**已经在菜单22/24/36/52 各写了一遍并且已经漂移**（例如菜单24 给水面加了 +z 凸出 2m，菜单36 重建时又没有）。再抄一份只会制造下一次不一致。
- **解法**（菜单53）：直接**采样场景里真实存在的地面网格世界顶点**（44297 个）建高度场，取水平容差内最高 y 当地面，按"埋入自身高度 25%"重坐。
- **验证**：幂等 —— 连跑两次第二次报 `moved 0 kept N`，说明收敛而不是反复抖动。
- **教训**：**永远以"画面里实际有什么"为准**，不要维护一份并行的解析模型。

### E-8 散布尺寸要按像素反推

- **现象**：撒了 179 颗卵石，画面上完全看不见，远岸仍然光秃。
- **真因**：scale 0.055~0.175 → 直径 0.12~0.39m，在 20~25m 外只有 **1~3 像素**。
- **解法**：改成 0.16~0.40（直径 0.35~0.9m）。
- **教训**：**程序化散布的尺寸要按"它在画面里占几个像素"反推，不是按米。** 同类错误：荷叶尺寸从"9-14cm"的错单位估算一路改到按 glb 实际尺度反算（见 F-1）。

### E-9 散布密度要按视线方向加权

- **现象**：均匀绕圆撒的道具，画面里看着还是稀。
- **真因**：相机 yaw 9° 意味着视线朝 +z，均匀撒的话密度全花在画面外的近岸和两侧。
- **解法**：额外补 5 簇专门落在 θ≈π/2 那一侧。

### E-10 移动带子节点的物体：不要手算锚点

- **现象**：编译报 `CS0019: Operator '*' cannot be applied to operands of type 'Vector3' and 'Vector3'`；而且手算的公式**漏了父节点的旋转**。
- **解法**（与旋转/缩放都无关的两步写法）：
  ```csharp
  t.localScale = new Vector3(sc, sc, sc);           // 先改缩放
  t.position  += (target - keep.position);           // keep.position 每次现算世界矩阵
  ```
- **教训**：**子节点的 `position` getter 实时反映父矩阵**，拿它当锚点天然正确。别去拼 `localPosition * lossyScale`。

### E-11 灌木读成石头 = 单块扁石 + y 缩放小于 xz

- **现象**：64 丛"灌木"在图上是一堆绿色铺路石。
- **真因**：复用了巨石的 `BuildFacetedRock(lump=0.22)`（一个扁圆石团），再乘上 `PlaceBoulder` 的 `y = s*(0.65~0.95)`、`xz = s*(0.85~1.25)` —— 纵向被压得比横向还扁，尺寸还给到 0.5~1.6m。低模里"扁 + 单块 + 大"三样齐全就是石头。
- **解法**：① 把 3~5 团扁叶丘**合并成一个网格**（轮廓立刻从"一个穹顶"变成"几个包"），6 个变体共享，避免生成 92 份网格资产；② 尺寸收到 0.34~0.80；③ 缩放改成 **y ≥ xz**；④ 颜色压暗。
- **教训**：低多边形风格里**轮廓比贴图重要**。同一套基础网格，改变"团块的组合方式"比换材质有效得多。

### E-12 散布物要按"离镜头多远"设下限，不是只按"别长在相机身上"

- **现象**：画面左下多出一根斜穿的锥形暗条，占约 310 像素。
- **真因**：一株 `PondTree_04` 落在离相机 **5.83m** 的位置（菜单63 的绕潭树环**完全没有**相机排除，菜单68 只排 3.5m）。交付树的枝桩是真实几何，不是贴图，近到一定程度必然穿帮。
- **解法**：`PlacePondTree` 统一加 6m 的 XZ 闸门（`BuildTreeWall` 里原来那份 3.5m 一并删掉，同一个物理量只留一处写入），被剔的株写 `SKIP-CAM <名> at <坐标>`。
- **教训**："别把树长在相机身上"和"别把树长在近到会穿帮的地方"是两条不同的判据，后者要按**物体自身尺寸**算，不是按碰撞半径。

### E-13 浪幅的上限是**机位高度**定的，不是审美定的

- **现象**：海岸第三版，画面左 60% 全是水，沙滩被挤成右下角一条 —— 像是相机掉进了海里。
- **真因**：最大波峰高度 = Σa·_SwellAmp·_ShoalGain（三条浪振幅之和 × 浅水放大）。机位当时站在 `up=15m`，那里沙面只抬到 1.3m、眼高 2.94m，而 Σa·1.5·2.1 ≈ 4m ⇒ **相机整个泡在浪头里**。
- **解法**：机位退到滩肩（`up=26m`，沙面已高于水位 2.9m，眼高 4.5m+），振幅才敢给回 1.0。
- **教训**：任何有垂直位移的水体，先算 `Σ振幅 × 最大放大倍率` 和"眼高减水面静高"的关系，再谈好看。反过来也成立：**机位高度一旦改动，水体振幅必须重审。**

## F.  资产 / GLB / 材质

### ★F-1 glb 的单位可能完全不是你以为的

- **现象**：低机位下荷叶像木筏。探针实测 `scale=0.15 → 直径 4.26m`，即该 glb 在 scale=1 时约 **28.4m**。
- **真因**：早期注释写的"9-14cm"是**按错误单位估的**，之后所有尺寸都建立在它上面。
- **解法**：**先量出 glb 在 scale=1 下的真实尺寸，再从目标直径反算 scale**：`sc = 目标直径 / 实测直径`。
- **教训**：**导入外部模型第一件事是量包围盒**，不要信文件名、缩略图或注释里的尺寸。

### ★F-2 glb 内嵌材质不可写，只能整只 Renderer 覆盖

- **现象**：给荷叶/荷花改了材质表里的颜色，没反应。
- **真因**：菜单48 的 albedo 字典只 `LoadAssetAtPath<Material>("Assets/Art/Materials/<名字>.mat")`，**碰不到 glb 内嵌的材质**（gltfast 生成的材质在 `.glb` 资产内部）。
- **解法**（菜单56 `ForceMat()`）：实例化之后遍历 `GetComponentsInChildren<Renderer>(true)`，把 `sharedMaterial` 整个换成自建材质。
- **两条子教训**：
  - **荷花要双面**：`_Cull = 0`。荷叶"一圈黄边"根本不是高度问题，而是**模型背面本就是黄色**、背面剔除让它露了出来。双面 + 正反面同色一并解决。
  - 想按物体类型定向替换时，先**打印 Renderer 名 + 原材质名**再决定映射规则，别猜。（本项目做法：菜单里塞一个 `diag < 6` 的探针输出。）

### F-3 材质是"实例快照"，改资产不生效

- **现象**：菜单里 `SetColor` 改了资产，渲染颜色纹丝不动。
- **真因**：场景对象（尤其 prefab 实例）渲染的是**材质实例快照**而不是资产引用。
- **解法**：菜单23「强制重挂场景全部材质」—— 按 `sharedMaterial.name` 去 `Assets/Art/Materials/` 找同名资产重挂。
- **教训**：**改资产 ≠ 改场景里的引用。** 需要一步显式的 rebind。

### F-4 gltfast 的 GLB 在手动 `cam.Render()` 下不渲染

- **现象**：非 Play 的截图里树/荷叶"消失"，而且连续两次截图**字节级完全相同**。
- **真因**：① gltfast 导入的 GLB prefab 实例在编辑器手动 `cam.Render()`（桥截图机制）下不渲染；② 水面 shader 的 `_Time` 在非 Play 也冻结。
- **解法**：GLB 物体用**场景文件核对**（`Main.unity` 里 `SmallLily_*` 的 m_LocalScale / `Tree_ring_*` 数量），或进 Play 亲验。
- **教训**：**"两次截图一模一样"本身就是个信号** —— 说明时间没走、渲染路径不对。

### F-5 UPM 版本号写错是静默失败

- **现象**：`.glb` 放进 Assets 只有 `.meta`、没有预制体。
- **真因**：gltfast 写了 6.4.1（**不存在**），manifest 解析失败但**不报错**，`packages-lock.json` 不更新。
- **解法**：先查注册表 `GET https://packages.unity.com/<包名>` 看 versions 列表；改完**重启编辑器**强制解析（UPM 文件监听不保证触发）。

### F-6 重建网格资产后 MeshFilter 引用变 null

- **现象**：删旧网格 + `CreateAsset` 重建后，场景里 `Water` 的 MeshFilter 显示 `m_Mesh = null`，水不渲染。
- **真因**：内存里的 `Mesh` 对象无法被序列化进场景。
- **解法**：重建后必须 `AssetDatabase.LoadAssetAtPath<Mesh>(path)` 取**资产引用**再赋给 MeshFilter。
- **配套**：就地覆写已有 Mesh 资产要用 `Clear()` + 逐字段赋值，**不能用 `CopySerialized`**（只复制序列化字段，GPU 顶点/法线缓冲会留空）。

### F-7 `instantiatePrefab` 会重置 localScale

- **现象**：实例化后变成 1×1×1。
- **解法**：显式传 `scale`。

### F-8 原语 Collider 类型不要写死

- **现象**：菜单12 第一版 `GetComponent<MeshCollider>().enabled=false` 拿到 null 抛空引用，`PondWall` 根本没建成，**但菜单按钮仍返回成功**。
- **解法**：改按通用 `GetComponent<Collider>()` 再 `DestroyImmediate`。
- **教训**：**运行后必须用 `findGameObjects` 点名验证实际产物**，不能只看菜单返回。

### ★F-9 Blender 导出的 FBX：轴转换挂在**根节点 transform** 上，不在网格里

- **现象**：按文档核对树高，`mesh.bounds.max.y` 读出 9.68，而文档写 12.6；摆放出来的树"高度对不上、还像躺着的"。
- **真因**：Blender 是 Z-up。Unity 导入器**不重写顶点**，而是把 −90° X 旋转挂在模型根节点的 transform 上。所以网格局部坐标里"高"在 **Z** 上、局部 Y 其实是进深；`01` 号局部是 `(7.94, 9.68, 12.56)`，真高 12.56 在 Z。
- **解法**：
  - **量尺寸只读 `Renderer.bounds`（世界包围盒）**，别读 `Mesh.bounds`。
  - **摆放时绕 Y 旋转必须"左乘"**：`inst.transform.rotation = Quaternion.Euler(0, yaw, 0) * inst.transform.rotation;`。直接赋 `Quaternion.Euler(0, yaw, 0)` 会把轴转换整个抹掉 → 树被放倒。
  - 同理，任何"复位 rotation 到 identity"的调试代码都会制造假故障 —— 本项目就在验收脚本里踩了这一次，报出"H 5.85 / W 12.56"，差点被当成资产导出错误。
- **教训**：交付说明里的数字没错，错的是我用哪个坐标系去读它。**先确认读数所在的空间，再判断谁对谁错。**

### F-10 `optimizeMeshData` / `importVertexColors` 在 2022.3.57 上取不到

- **现象**：按"要保住顶点色就得关 Optimize Mesh Data"的常识去设 `ModelImporter` 的这两个字段，`SerializedObject.FindProperty` 返回 null。
- **真因**：这两个序列化字段在该小版本不存在（或改名）。
- **解法**：不靠"设标志位"保证，改成**实测通道存在**：`mesh.GetVertexAttributes()` 里找 `VertexAttribute.Color`。验收菜单因此报的是 `vcol 有/无` 而不是"我设过了"。
- **配套**：2022.3 也**没有** `Mesh.GetChannelCount(MeshChannel)`（那是更新版本的 API），要用 `GetVertexAttributes()` —— 而且它不需要 Read/Write 就能调，正好配合交付说明"Read/Write 关"的要求。
- **教训**：版本相关 API 不要凭记忆写；拿不到字段时**换一个能直接证明结果的观测点**，而不是假设"我设了就应该生效"。

## G.  Unity 编辑器与 MCP 桥

### ★G-1 `runMenuItem` 永远返回 ✅，即使抛异常或菜单不存在

- **现象**：以为菜单跑成功了，实际什么都没发生。
- **解法**：**唯一可信的通道是往文件写探针**（本项目：`Logs/water_probe.txt`）。每个菜单开头/结尾各写一行，失败写 `FAIL`。
- **配套**：整链重建菜单（57）在**每一步之前**写 `STEP n`，中途炸了能定位。

### ★G-2 `runMenuItem` 会把 Unity 最小化 → 截图永不落盘

- **现象**：菜单43 在探针里写了 `captured`，但 `_gameview.png` 的 mtime 不动。
- **真因**：编辑器一旦最小化就不渲染，`ScreenCapture.CaptureScreenshot` 排队的帧永远不 flush。
- **解法**：**先跑截图菜单，再 `activate_window`** —— 被排队的帧会在恢复前台时补写出来。反过来"先 activate 再截图"没用，因为截图那次调用本身又把它最小化了。
- **判据**：**比对目标 png 的 mtime 有没有前进**。只看"菜单返回 ✅"会把"材质没生效"和"根本没有渲染"混为一谈。

### ★G-3 退出 Play 模式**不一定**回滚场景改动

- **现象**：为了做近景检查，在 Play 里用桥把 `Main Camera` 挪到 `(0,1.6,-5.5)`，**退出 Play 后它仍是这个值**。
- **真因**：桥的 `setProperty` 走了 `Undo.RecordObject` + `SetDirty`。
- **解法**：临时改相机/物体做检查后，**必须读回属性确认**并手动复位，再 `saveScene`。
- **反向坑**：在 Play 里**创建**的物体（菜单55/58 的产物）退出 Play 就没了 —— 要么在编辑模式跑完再进 Play，要么退出后重跑。

### G-4 编辑器没有 Console 回读通道

- **现象**：`Debug.Log` 取不回来。
- **解法**：要拿实况就在菜单里**写到文件**再读。

### G-5 `Editor.log` 的行号和错误都是陈旧的

- **现象**：已经修好的 `receiveShadow` 报错仍显示在 3369/3411 行；grep 出来的 `error CS` 大部分是历史。
- **真因**：`Editor.log` 累积整个会话的所有编译输出；且文件含空字节，按 UTF-8 直接 grep 会漏。
- **解法**：`Tools/check_compile.sh` —— 先快照字节偏移，**只看新增部分**；读之前 `tr -d '\000'`。
- **教训**：**判断当前编译状态用"新代码里才存在的菜单能不能跑"，不是比对 dll 时间戳、更不是读日志。**

### G-6 Auto Refresh 是关的

- **现象**：`refreshAssets` 之后 C# 没重编译。
- **真因**：`Assets/Refresh` 和进 Play 模式都**不保证**触发脚本编译，必须让窗口**获得一次焦点**。
- **补充**：改 `.mat` / `.shader` / URP `.asset` **不需要**焦点，`refreshAssets` 就立即生效（shader 只重编译着色器，不等域重载）。**所以纯调参可以在 Play 里连续迭代，不必每次退出重编重跑整链** —— 这是本项目后期最高效的工作方式。

### G-7 `GameObject.Find` 找不到 inactive 对象

- **现象**：`setProperty active=false` 之后，再想 `active=true` 恢复时桥报"not found"。
- **解法**：靠退出 Play 回滚，或先确认自己能恢复再隐藏。

### G-8 undo 栈混着所有 MCP 写操作

- **现象**：连续 undo 把更早的改动（如 transform 缩放）一起回退了。
- **教训**：撤销后要复查关键字段。

### G-9 工具参数格式不统一

| 工具 | 坑 |
| ---- | -- |
| `setProperty` | Vector 要传**对象** `{"x":1,"y":2,"z":3}`，传 `"1,2,3"` 报 schema 错 |
| `setComponentProperty` | Color 用 `"r,g,b,a"` **字符串**，枚举用名字 |
| 两者 | Transform 的 `m_LocalRotation` 是 Vector4，**都写不了** → 转欧拉角走 `setProperty` |
| `setMaterial` | 只命中"该对象或其子对象里**第一个** Renderer"，多材质物体无法定向替换 |
| `deleteGameObject` | 参数名是 `gameObjectName`，不是 `name` |
| `createScene` | Additive 模式遇未命名场景会失败 → 用 `NewSceneMode.Single` |
| `addComponent` | 带命名空间的类名不认 → 桥按类名模糊匹配 |

### G-10 多编辑器并存时 MCP 会串台

- **现象**：`unity_getSceneHierarchy` 静默返回了**另一个项目**的场景，`unity_ping` 照样回 pong，完全看不出来。
- **真因**：全局 MCP 配置不带 `--port=`，回落到 6400 打到别人的编辑器。
- **解法**：项目专属端口写进 `.qoder/settings.local.json`；**写操作前先 `getSceneHierarchy` 确认根节点里有本工程的标志物**。
- **注意**：已在跑的 node 客户端**不会**改端口，换端口后要 `/mcp reload`。

### G-11 结构性编辑事故：插入新菜单吃掉下一个菜单

- **现象**：把菜单51/53/54 插到菜单52 之前时，多带了一个类闭合花括号 `}`，导致菜单52 掉到类外。
- **解法**：恢复尾部 + 删掉多余的 `}`（C# 成员顺序无关）。
- **教训**：**在长文件里插代码，锚点要包含下一个成员的完整签名**，不能只锚注释行。

### G-12 复刻视频取帧：接口拉不到就截屏

- **现象**：抖音页面是 JS 空壳、接口全被风控，无法服务端拉流抽帧。
- **解法**：浏览器打开视频 URL → 等播放 → PowerShell `CopyFromScreen` 连拍多帧 → 裁播放区 → 对比分析。

### ★G-13 `EditorSceneManager.NewScene` 在 Play 模式里直接抛异常，而且你看不到

- **现象**：整链建潭菜单跑了，探针里只有 `MENU64 begin` 一行，后面什么都没有；`runMenuItem` 照样回 `✅ Executed`。控制台里躺着一句 `InvalidOperationException: This cannot be used during play mode, please use SceneManager.CreateScene() instead.`
- **真因（两层叠加，这才是难查的地方）**：
  1. Play 模式下不能 `NewScene`；
  2. **Unity 会把脚本编译推迟到退出 Play** —— 所以我这次跑的还是**改动前的旧代码**，而旧代码里没有 Play 模式判断。
     我在 Play 里改了 C#、`refreshAssets`、然后直接跑菜单，全程以为改的是新代码。
- **解法**：菜单开头显式挡掉并写探针：
  ```csharp
  if (Application.isPlaying) { WriteProbe("MENU60 REFUSED: 在 Play 模式，先退出\n"); return; }
  ```
  同时整链菜单改成**逐步写 `STEP n` + try/catch**，中途炸了能立刻定位是哪一步。
- **教训**：**凡是会改场景生命周期（NewScene / OpenScene / 建资产）的编辑器菜单，都必须自带 Play 模式守卫。**
  另外：**改完 C# 一定要先确认已经退出 Play 并真的重编了**，否则"改了没生效"会被误读成"我的改法不对"。

### G-14 `check_compile.sh` 只 grep `error CS`，漏掉整个 shader

- **现象**：`check_compile.sh` 报"无错误"，但水面 shader 其实编译失败（见 A-7）。
- **真因**：脚本只匹配 `error CS[0-9]+`，而 shader 报错的格式是 `Shader error in '<名>': ...` / `undeclared identifier`，完全不在匹配范围内。
- **解法**：把 `Shader error in` 和 `undeclared identifier` 加进 grep。
- **教训**：**"我的检查通过了"不等于"我检查的东西通过了"** —— 工具覆盖面要先对上会出错的种类。这条和 B-1、G-13 是同一类失误：**验证手段本身有盲区，而盲区里恰好藏着 bug。**

### ★G-15 调试通道看到的"正常"，是合成之后的正常

- **现象**：`_DebugMode 1` 直接 `return planar`，画面上确实"有倒影的形状"，于是判定"反射内容没问题，是强度/混合不对"，接着在水面上连调 `_PlanarStrength`/`_SkyReflect`。全部无效。
- **真因**：所谓"直接输出 RT"仍然经过了一整条链：RT 是**线性 HDR**（子相机关了后处理），主相机再过一遍 ACES；而且采到的 UV 本身是错的（裁剪平面翻了符号 → 采到的是潭底）。形状看着"像树"，是因为潭底底盘的椭圆轮廓被误读成了岸线。
- **解法**：加**菜单67「导出平面反射RT」**，把子相机的 RT 原样读成 PNG（`RenderTexture.active` + `Texture2D.ReadPixels` + `EncodeToPNG`，落在 `Docs/screenshots/_pond_rt.png`），**绕开水面合成**直接看反射相机自己看到了什么。
- **战果**：这一张图一次定位了三个 bug —— 镜像相机绕视轴滚 180°（D-14）、裁剪平面被取反成保留水面以下（D-15）、以及后来确认"反射其实一直是深色的所以累加必然洗白"（D-13）。在此之前我在合成端试了至少四种参数组合。
- **教训**：**观测通道必须比被观测量更接近源头。** 水面 shader 的"更接近源头"就是那张 RT。凡是"调试输出看起来正常但结果不对"，先怀疑**输出通道本身被污染了**，而不是继续在被污染的读数上调参数（与 I 节"用被污染的仪表做诊断"同一条）。

### G-16 取导入器只能用 `AssetImporter.GetAtPath`

- **现象**：导入设置菜单对每个文件都报 `MISSING Assets/Trees/FBX/...`，但文件确实在磁盘上、也进了工程。
- **真因**：写成 `AssetDatabase.LoadAssetAtPath<Object>(path) as ModelImporter` —— 对 `.fbx` 返回的是**模型根 GameObject**、对 `.png` 返回的是 **Texture2D**，`as` 到导入器**恒为 null**。
- **解法**：`AssetImporter.GetAtPath(path) as ModelImporter / TextureImporter`。同时把"文件不在磁盘"和"导入器取不到"分成两条报法，否则这两种完全不同的故障会共用一句"MISSING"。
- **教训**：**"我的代码说文件不存在"要先怀疑是我读文件的方式错了**，再怀疑文件。

### ★G-17 活干完了、只是日志行炸了 —— 这不是失败

- **现象**：`菜单72` 只打出 `begin` 就没了，`runMenuItem` 照例回 ✅。看起来像"Prefab 一个都没生成"。
- **真因**：`DestroyImmediate(inst)` 之后又去读**销毁前缓存的 `Renderer[]`** 统计槽数 → `MissingReferenceException`。而 `SaveAsPrefabAsset` 在那之前就已经执行完，**5 个 Prefab 其实全部落盘了**。
- **解法**：① 所有要在销毁后用的读数，**销毁前取好存进局部变量**；② 整链菜单**每一步各自 try/catch 并把异常类型+消息写进探针**，别让一步的异常吞掉后面四步、也别让异常和"没做"长得一样。
- **教训**：`runMenuItem` 的 ✅ 不含信息（G-1），而**未捕获的异常也不含信息** —— 它只让"成功"看起来像"失败"。判据只能是磁盘上的实际产物（`ls Assets/Trees/Prefabs/`）。

### ★G-18 编辑器最小化时主相机**根本不渲染**（而子相机 RT 还会给你残帧）

- **想解决的问题**：`ScreenCapture.CaptureScreenshot` 只在编辑器处于前台时才落盘，于是要做一个"最小化也能取图"的通道。
- **两条试过都失败的路**：
  1. `cam.targetTexture = rt; cam.Render();` 同步渲 —— **图能拿到，但不走 URP 后处理**（ACES/Bloom/Vignette 全无）。自检里四角/中心亮度比 `1.093`（>0.88 即无暗角）当场证伪，这张图不能当验收依据。
  2. 把主相机 `targetTexture` 指向 RT，挂 `RenderPipelineManager.endCameraRendering` 等 URP 在正常帧循环里渲完再取 —— **回调永远不来**：编辑器最小化时 Game 视图整条渲染被跳过。
- **最阴的地方**：菜单67 读**镜像相机**的 RT 在最小化时是"成功"的 —— 它读到的是**上一次前台时留下的残帧**。所以"后台能拿到画面"这个结论会被一次假阳性坐实。
- **顺带的危害**：方案 2 把 `targetTexture` 挂上去之后没有回调来还原，用户一旦把窗口切回前台，Game 视图会是黑的（主相机还在往一块已销毁的 RT 渲）。该工具已删除。**做调试工具时要问一句：它失败的时候会不会把工程弄坏。**
- **结论**：要拿**带后处理**的真实画面，只有让编辑器处于前台这一条路。判据仍然是"**mtime 有没有前进**"，而不是探针写了 `captured`。

### ★G-19 `runInBackground: 0` 让后台截图变成"过期照片"

- **现象**：菜单65 连续三次出图，**PNG 的 md5 完全相同**，`Time.frameCount` 冻在 3。期间我在 Play 里把 5 个光柱物体 `active=false` —— 这种一眼该看出来的改动，在"新截图"上一动不动。
- **真因**：`ProjectSettings/ProjectSettings.asset` 里 `runInBackground: 0` ⇒ 编辑器一失焦，Play 循环整个停摆，`GameView.m_RenderTexture` 永远停在最后一次前台渲染。这条与 G-18 是同一个病的两面：G-18 说"最小化时主相机不渲染"，这里补一句 —— **而且它会把上一次的 RT 留在原地等你读**。
- **解法**：抓取前置 `Application.runInBackground = true`，再挂 `EditorApplication.update` 等 `Time.renderedFrameCount` 至少前进 3 帧才动手；**超时写 `MENU65 STALE` 且不覆盖旧图**。
- **教训**：判据要从"mtime 有没有前进"升级成"**帧计数有没有前进**"。mtime 前进只证明文件被重写，不证明内容变了。取图通道必须自带一份"我拿到的是新帧"的证据，否则它会持续、安静地喂你过期画面，而你会拿过期画面去否定真实的改动。

### ★G-20 肉眼二分掉六个组之后，才肯写一条像素探针

- **现象**：还是那根暗条。
- **走过的弯路**：在 Play 里逐个 `active=false` 再截图，连续排除了光柱 → 倒木 → 林线 → 冠层 → 绿坡 → 沙岸**六个组**。每轮"改 + 抓 + 看图"约一分半，六轮下来近十分钟，信息量为零。
- **解法**：新增 `菜单69「像素探针」`：`cam.ViewportPointToRay` + `Renderer.bounds.IntersectRay`，按进入距离排序，把候选物体的名字、材质、包围盒尺寸一起写进探针。**一次调用**锁定 `PondTree_04 @ 4.36m`。
- **教训**：二分法只在"候选集小、且每次判定便宜"时才划算。当判定本身要跑一整条渲染管线时，**写一个直接问几何的工具几乎总是更快**。与 G-15 同一条：观测通道必须比被观测量更接近源头。

### ★G-21 `Editor.log` 会**整段停止增长**，于是"日志里没有 shader 错误"一文不值

- **现象**：海面品红，我去 `%LOCALAPPDATA%\Unity\Editor\Editor.log` 找编译错误 —— 尾部 600KB 里 `Shader error` 零条，`Water_Ocean` 这个词一次都没出现。而我**刚刚**才在里面读到过 6 条 `Shader error in 'WaterProject/Water_Ocean'`。文件大小连续两次测都是同一个数（16602217）。
- **真因**：编辑器不 flush 时 `Editor.log` 可以长时间不落盘。加上它被本机所有 Unity 编辑器共用（《05》G 章反复提过），"没有错误行"既可能是真没有，也可能是**这条通道此刻根本没在写**。这两种情况在文件里长得一模一样。
- **解法**：改读 `Logs/shadercompiler-UnityShaderCompiler.exeN.log`（工程目录下）。这些是编译**子进程各自**追加的，每编一个 shader 一条，实时。判据取**字节增量**：先记各文件 `wc -c`，改动后只看新追加的那段里的 `error:` —— 因为这些日志是追加式的，旧错误会永远留在文件里，直接 grep 会追一个已经修掉的鬼。
- **已固化**：`Tools/check_shader_errors.sh mark` / `Tools/check_shader_errors.sh`。
- **教训**：这是 G-19 的同类 —— 一个会**喂过期内容**的通道比一个会报错的通道危险得多，因为它让你有理由相信"查过了"。

## H.  C# 编译错误速查

| 报错 | 原因 | 修法 |
| ---- | ---- | ---- |
| `CS0234 'UnityEngine.AmbientMode' does not exist` | 文件已 `using UnityEngine.Rendering;` | 写 `AmbientMode.Trilight`（不带 `UnityEngine.` 前缀） |
| `CS1061 'MeshRenderer' does not contain 'receiveShadow'` | 2022 里是复数 | `receiveShadows` |
| `CS0019 Operator '*' cannot be applied to Vector3 and Vector3` | 没有逐分量乘法 | `Vector3.Scale(a,b)`，或改走父/子变换（见 E-10） |
| `CS0136 local or parameter 'y'/'r' cannot be declared` | 与外层同名 | 换名字（`foreach` 变量尤其容易撞） |
| `CS1061 'GameObject' does not contain 'fieldOfView'` | GameObject 上没有 | `cam.GetComponent<Camera>().fieldOfView` |
| `CS1061 'Camera' does not contain 'AddComponent'` | Camera 是 Component 不是 GameObject | `sv.camera.gameObject.AddComponent<...>()` |
| `CS1061 'Enumerable.Range'` | 文件没有 `using System.Linq;` | 改普通 for 循环 |
| `All compiler errors have to be fixed before you can enter playmode!` | 有编译错时 `runMenuItem` **照样返回 ✅** | 先清编译错再判断菜单是否真的跑了 |

## I.  误判记录（我错在哪，为什么错）

> 这一节比任何技术结论都有价值：**错误的诊断会让我在正确方向上持续投入**。

| # | 我当时坚信的结论 | 实际 | 我是怎么被误导的 |
| - | ---------------- | ---- | ---------------- |
| I-1 | "深度纹理没启用" | 深度纹理一直是好的，坏的是取它用的 UV | 诊断数据本身来自 A-1 那个坏通道 —— `screenUV` 恒为 `(1,0)`，取到的是画面右上角的污染值。**用被污染的仪表做诊断，结论一定被污染。** |
| I-2 | "ACES 把画面压暗了" | Volume 从没落盘（B-1），ACES 根本没生效 | 画面确实暗，但原因在别处。**"某个后处理在伤害画面"的前提是它真的在运行。** |
| I-3 | "沙滩太亮，要压暗" | 是**缺蓝**，压暗只会变脏灰 | 只看明度没看色相分布。 |
| I-4 | "远山太亮，要压暗" | 是**色相顺序错**（绿 > 蓝，应为蓝 > 绿） | 同上；而且"压暗"直接得到黑三角剪影。 |
| I-5 | "岩石近黑 = 反照率太低" | 是**环境光被压太低** | 没先量参考帧的"受光/阴影比"（C-2）。改了三轮反照率才想到去看光源。 |
| I-6 | "提 ambient 没用" | ambient 确实提了，但**太阳仰角被菜单54 覆盖**（C-4） | 两个原因互相掩盖，而我假设"我改的就是生效的"。**从没验证过覆盖关系。** |
| I-7 | "碎闪太弱 = 强度不够" | 是**角速度参数把高光限制在极小区域**（D-4） | 强度确实"没起作用"，但我把"没起作用"归因于"还不够大"，而不是"这条路根本没开"。 |
| I-8 | "浅滩灰带是几何问题" | 是**池底色相问题**（D-7） | 连着改了三个几何参数都无效，才想到用排除法。**应该一开始就先定位归属，再修。** |
| I-9 | "沙滩消失了 = 材质不对" | 绕序反了 + 背面剔除，**它根本没被画**（E-1） | 默认"看得见 = 画了"。 |
| I-10 | "荷叶 9-14cm" | glb 在 scale=1 下是 28.4m（F-1） | 沿用了注释里的错单位估算，之后所有尺寸都建立在它上面。 |
| I-11 | "截图没变 = 我的改动没生效" | 截图通道在喂**过期帧**（G-19） | 我用"图没变"去否定改动，却没先证明"图是新的"。**任何"改了没反应"的结论，前提是先验证反馈通道本身。** |
| I-12 | "那根暗条是水面着色器的问题" | 是一株 5.8m 外树的枝桩（E-12） | 它画在水面上、看起来就像水的条纹。**位置相近不等于归属相同** —— 与 I-8 是同一类错误，我犯了第二次。 |
| I-13 | "URP 自己就是 include 里开 `UnityPerMaterial`、shader 再开一个同名块，所以我也能" | 它开的是**另一个名字** `UnityBuiltinPerMaterial`；同名块 fxc 直接拒编（A-10） | 用一个**记错的权威先例**去支持一个没验证的假设，比凭空猜更糟 —— 它让我觉得不用再查。**引用框架源码前先 grep 源码。** |
| I-14 | "audit_materials.py 报 ERROR 0，所以材质层是干净的" | 脚本自己有 3 个 bug：数组声明解析不到、注释里的 token 被当声明、材质归属数据流没接上 | 新写的检查工具**首轮全绿**这件事本身就该可疑。验证办法是故意制造一次违规（把块名改回去）看它报不报。 |

### 从这些误判里提炼的三条元规则

1. **先验证观测通道，再验证被测量。**（A-1 / B-1 / B-2 / G-1 / G-2 全是这一条）
   具体做法：做一次**极端值测试**（postExposure 设 -4、颜色设纯红）。画面没变 → 通道不通，别再解释"为什么是这个值"。
2. **改完没效果时，第一反应应该是"我改的东西真的生效了吗"，而不是"还不够"。**
   具体做法：grep 这个属性被写了几次（C-4）；读回资产确认落盘（B-1）；比对截图 mtime（G-2）。
3. **多原因叠加时会互相掩盖，单变量实验失效。**
   具体做法：把耦合系统（光照/后处理/材质）按**固定顺序**分层调 —— 曝光 → 光源 → 反照率 → 色相，每层收敛了才进下一层（C-1）。
